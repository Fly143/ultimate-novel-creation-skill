## 4.1b `--stop-at-dashes` 的污染原理

第 1/2/4 项实现（`fingerprint.py` / `.pl` / `.ps1`）**不支持** `--stop-at-dashes`，只有 `fingerprint.byte.pl` 与 `wordfreq.byte.pl` 支持。正文末尾带 `----` 元数据块 + YAML 的章节：用前三项会把元数据当正文统计，句长方差/段落数/对话占比全被污染，而修复子代理正是按这些数值"改分布"，等于把修复导向错误方向。正文末尾无该块的章节无需该旗标。

## 分布"防过度"的完整口径

- 拉大方差靠**长短自然交替**：长句内部加逗号节奏、关键处用短句强调。
- **禁止**把长句机械切成碎片凑方差；**短句连篇**（方差反而很低）也勿强拉长句。
- 修复后通读改动段落：出现"碎句堆砌 / 一句一段 / 读起来断断续续" → 优先回退为长句微调，而不是继续切短。
- 分布区间是"像不像人"的参考，**不是牺牲通顺的硬指标**：通顺与方差冲突时通顺优先，报告注明 `note: distribution relaxed for readability`。

## state_commit delta 事务文件字段格式（完整自查清单）

`draft` 生成空事务 JSON 后，填 `delta` 时**必须**满足以下格式要求。每条不满足都会在 `commit` 阶段才报错（不在构造时静默通过），反复 read-modify-retry 浪费 5–10 分钟。填完后逐项自查再提交。

### context.position 须为对象

`delta.context.position` **必须是对象**，不能是字符串。正确格式：
```json
"position": {
  "city": "临江市",
  "location": "异能学院训练场",
  "chapter": "第7章"
}
```
写成 `"position": "第7章"` 触发 `delta.context.position 须为对象`。

### summaries / wordcounts 键须为十进制数字字符串

`delta.summaries` 和 `delta.wordcounts` 的**键**必须是纯数字字符串（`"7"`），**不能**用 `"第7章"` / `"第007章"`。写错触发 `summaries 键必须是十进制数字字符串（≤18 位）`。

### foreshadow 条目须为对象

`delta.foreshadow` 的**每个值**必须是对象（含 `desc` / `status` 字段），不能是字符串。写错触发 `foreshadow.XXX 须为对象`。同时，条目内部的 `planted_ch` / `planned_resolve_ch` / `resolved_ch` **必须写整数**（`1`、`0`），不可写字符串（`"1"`）——会触发 `TypeError: '<' not supported between str and int`。

```json
"foreshadow": {
  "烧穿风险": {
    "desc": "攒满自爆型，断则烧穿不可逆",
    "status": "active",
    "planted_ch": 7,
    "resolved_ch": 0
  }
}
```

### facts 条目须为对象

`delta.facts` 的**每个元素**必须是 `{fact, category}` 对象，不能是裸字符串。写错触发 `facts 条目须为对象` 或合并校验失败。

```json
"facts": [
  {"fact": "唐晓棠的线从心口到指尖约70公分", "category": "bug细节"}
]
```

### draft → fill → commit 工作流

1. `python scripts/state_commit.py draft --project "[路径]" --chapter N` — 生成空事务模板到 `.story/work/第NNN章/state.json`
2. 读取模板，填写 `delta` 所有字段（按上述格式要求）
3. `python scripts/state_commit.py commit --project "[路径]" --chapter N --input ".story/work/第NNN章/state.json"` — 提交事务

### timeline / characters / overview 结构

- `timeline` 为对象：`readers_known` 和 `authors_truth` 均为字符串数组
- `characters` 为对象：每个角色为 `{change, status}` 对象
- `overview` 为对象：含 `stage` / `progress` / `chapter_count` 字段

## 写作子代理后校验：ASCII引号·UI文本·禁用词·段落句长·时间指代

写作子代理常无视"必须用中文弯引号"的指令，返回的正文里混入 ASCII 双引号（`"`）。同理，文风设定中的"每段最长不超过N句"约束、去AI化禁用词规则也可能被忽略，甚至出现游戏UI风格文本，且默认用"昨天"指代过去事件（不知故事中"今天"是第几天）。03_06 步骤4 保存正文后应增加五项机械校验，命中后**批量替换/定点拆段/定点改写**，不退回子代理（机械操作比重写快且安全）：

1. **ASCII 引号扫描**：`python -c "import sys; t=open(sys.argv[1],encoding='utf-8').read(); n=t.count('"'); print(f'ASCII双引号:{n}个')" "正文文件路径"`。命中 >0 → 按开闭替换为中文弯引号（`"` → `“`/`”`，`'` → `‘`/`’`），重新保存。
2. **段落句长上限核对**：若文风设定「每段上限句数」字段有具体数值（>0），保存后逐段统计句数（按句末标点 `。！？` 切分），标记超限段落 → 退回子代理**定点拆段**（指明第几段、当前句数、目标上限），禁止全文重写。
3. **游戏UI文本扫描**：保存正文后扫描 `【` / `】` 字符，命中即定位并改写为角色内心感知/叙述性描写（保持原信息量，仅换表达形式，如 `【已使用：一】` → `第一格，灭了。`）。此检查与 ASCII 引号扫描同批执行。
4. **一级禁用词扫描**：wordfreq 脚本输出的 ❌ 高危词命中即替换（瞬间→那一刻/当时、然而→但/结果、深吸一口气→直接删或改角色动作）。此检查与 wordfreq 脚本同批执行。
5. **时间指代词扫描**：写作子代理不知故事中"今天"是第几天，默认用"昨天"指代过去事件，高频与已确立时间线矛盾（已观测：第8章"昨天"×7全部与"第4天下午"矛盾，其中3处事件前7章无出处，1处与第6章实测直接冲突）。扫描 `昨天/前天`，逐处核对 `记忆系统/上下文.md` 的当前章节位置——时间指代错误 → 改为正确的故事日参考（"中午""上次""之前"）；该时间指代的事件在前文无出处 → 改为模糊指代（"上次""之前"）或删去。此检查与 ASCII 引号扫描同批执行。

这五项与人工种子核对（步骤4 第7条）并列，均不省略。

> **修复/强化轮同样适用**：4.3 修复子代理与 4.1e 强化轮改稿后可能引入新的半角引号。改稿交付后必须重跑 ASCII 引号扫描，命中>0 → 批量替换为全角弯引号，再进入下一步。此检查与 `text_guard digest` 同批执行，不额外占用独立步骤。

## 修复优先级：改最少原则的具体化（防「全改」与「全不改」两个极端）

> 本条澄清 03_26 步骤4.3「全量修改所有标记」与同模块「改最少原则/防过度」的张力；03_26 正文应同步修订为按本条分级（此处为设计说明，动作权威仍在 03_26）。

U 分级返回时按等级取**最小必要改动集**：

- ❌ FAIL（逻辑硬伤/跨章矛盾/OOC/因果断层/设定矛盾）必修。
- 🟡 低优建议项**评估后部分可不改**，须在报告修复记录注明理由。可不改的典型：①合规压线（环境描写压线句数上限但毛边细节到位、句长方差偏低但属短句流文体特征）②核心爽点故意留白（智斗翻盘不交代战力机制、章末悬念故意不闭环）③改动会破坏 prose 性格或引入 AI 腔。

改最少 = 「必修项全修 + 建议项按影响评估取最小集」，非「全改」也非「全不改」。跳过项必须在报告修复记录写明理由（哪条、为何可不改），供用户复核。

**流程边界**：本流程（U 审核修复）的「改最少」与独立子代理审计的「全量修🔴🟠🟡🟢四级」是两条独立流程，不互相套用——审计铁律要求全量修四级属另一质量门禁，不因 U 审核修复跳过低优建议项而违反审计铁律，也不因此放松 U 审核修复的必修项。

## 强化轮改动字数后必须重跑 state_commit

4.1e 强化轮（人工证据强化）可能大幅改动正文——字数变化会影响 state 事务中的字数记录。强化轮交付后必须重跑三步：

1. `text_guard digest --chapter N` — 刷新指纹为最终稿
2. `state_commit commit --chapter N` — 用更新后的字数重建事务 JSON 重新提交（`.done/第NNN章_state.done` 由脚本自动覆盖）
3. `check-done` — 复核闭环标记仍全齐

若跳过第2步，`.done` 标记仍在但字数与正文不符，后续跨章一致性检查会误报。此三步在强化轮「更新报告后再向用户汇报」之前执行。
