# 功能模块 26：写后流水线（强制·每章必跑·v9.3 单子代理合并版）
>
> **功能编号**：26
> **功能定位**：单章正文通过字数检查后，执行"主代理记忆维护 + 子代理审核 + 子代理修复"的完整闭环。
> **架构版本**：v9.3 — 在 v9.2（3 子代理单批并行）基础上，将 3 个审核子代理进一步**合并为 1 个全量审核子代理 U**（A/B/G/C/F/D/E 全 7 项一次出报告）。仍是 `delegate_task` 独立子代理，不降级为主代理自审（铁律不变）。修复子代理仍独立，保证"审核与修复分离"避免自审偏见。
> **铁律**：第 N 章全部 PASS + .done 标齐，**才允许写第 N+1 章**。黄金开篇"第1-3章"也必须逐章闭环，禁止连写再补审。

**执行逻辑**：
1. 检查 `[书名]/记忆系统/bible/` 目录下的 5 个圣经文档是否全部存在：

3. **任一缺失** → **直接终止**，提示用户执行功能18初始化记忆系统。记忆系统是写后流水线的硬性前提。

## 一、总流程（顺序不可跳）

```
1. 字数确认（复用 05_06 步骤4 脚本结果）→ 立即写入 `.done_wordcount`
2. 主代理更新 5 圣经 + 摘要 → 完成后写入 `.done_bible` + `.done_summary`
步骤3  单子代理 U（全量审核，合并 A/B/G/C/F/D/E 七项，一次调用）：
         读取全套文件 → 输出一份完整审核报告 → 末行三态总结
步骤4  收集结论 → 全 PASS 标 .done；有 FAIL → 独立修复子代理（只读 FAIL 报告+正文，不读记忆文档）
步骤5  周期检查（每5/10/50章触发）
步骤6  追加章节元数据
```

> **v9.3 架构变更说明**：
> - **3 审核子代理 → 1 全量审核子代理 U**：原 S1（A/B/G）、S2（C/F）、S3（D/E）合并为单个子代理 U，七项审查在一次调用内完成，输出一份报告。仍是独立 `delegate_task` 子代理，主代理不自审（铁律不变）。
> - **修复子代理保持独立**：审核（U）与修复由不同子代理完成，避免"自己查自己改"的自审偏见。
> - **B（强约束）仍始终 PASS**：并入 U 第二节，有风险时附加提示，零风险静默，不阻断流水线。
> - **审核子代理仍返回完整报告**：不再只返回 PASS/FAIL 一行。完整审核报告使得修复子代理可以直接读报告定位问题，无需重新加载全套记忆文档。
> - **修复子代理只读 FAIL 报告+正文**：不再需要读取记忆文档。审核报告已包含"具体段落引用→矛盾点→修改建议"，修复子代理按报告指示执行即可。
> - **.done 标记名全部保留兼容**：原 7 个审查标记（gates/constraints/logic_causal/review/quality/coherence/rhythm）名称不变，由 U 在同一步一次性写入。

## 二、步骤3 全量子代理 U 审核规格（★v9.3 单子代理合并版）

> **前置检查**：启动子代理前，验证 `delegate_task` 工具可用。若不可用 → 阻断流水线，提示用户检查 Hermes 配置后重试（不可降级为主代理自审，与铁律冲突）。
>
> **⚠️ 子代理启动前必须加载源模块**：详细检查维度与报告格式定义在对应源模块中。主代理在 invoke delegate_task 前，应读取以下源模块并将关键格式要求注入子代理 context：
> - B（强约束）→ `read_file("modules/05_22_功能模块.md")` 子代理调用规格节
> - C（读者审稿）→ `read_file("modules/05_25_功能模块.md")` delegate_task 调用模板
> - F（质量）→ `read_file("modules/05_13_功能模块.md")` 子代理调用规范
> - D（连贯性）→ `read_file("modules/05_17_功能模块.md")` 子代理调用规格
> - E（节奏）→ `read_file("modules/05_12_功能模块.md")` 子代理调用规格
> - A 五道门禁、G 逻辑因果为内联定义（下方已包含完整调用模板）。
>
> 通过 `delegate_task` **单次启动**全量审核子代理 U（`toolsets:["file"]`，U 可自行读取上述源模块获取详细格式）。
> context 必含：项目工作目录、章节文件名、所需读取文件清单、`mode: pipeline` 标识。
>
> **★ 关键：子代理返回完整报告，而非仅 PASS/FAIL。** 完整报告用于步骤4 修复子代理直接定位问题，无需修复子代理重读记忆文档。

**U 全量审核子代理调用规格（合并 A/B/G/C/F/D/E 七项·v9.3）**：

```
goal: 对第NNN章执行全量审核（合并原7子代理：五道门禁A + 强约束B + 逻辑因果G + 读者审稿C + 质量F + 连贯性D + 节奏E），输出一份完整审核报告

context: 中文回复。项目目录：{工作目录}，章节文件：{书名}/正文/第NNN章_章节名.txt。
  ⚠️ mode: pipeline — 由05_26写后流水线步骤3调用。返回完整报告正文（不再仅返回PASS/FAIL一行）。
  需读取文件清单（U 可自行用 file 工具读取）：
   - 章节正文：{书名}/正文/第NNN章_章节名.txt
   - 设定：{书名}/设定/{书名}_世界观设定.md、{书名}/设定/{书名}_人设卡.md、{书名}/设定/{书名}_情节大纲.md
   - 圣经：{书名}/记忆系统/bible/story_bible.md、character_arcs.md、plot_timeline.md、chekhovs_gun.md、character_database.md
   - 摘要：{书名}/记忆系统/summaries/ch_{NNN-10}_summary.md ～ ch_{NNN-1}_summary.md（前10章摘要，供连贯性/节奏/读者体验使用）
   - 详细格式与维度定义（U 应读取以遵循规范）：
       B 强约束 → modules/05_22_功能模块.md
       C 读者审稿 → modules/05_25_功能模块.md
       F 质量 → modules/05_13_功能模块.md
       D 连贯性 → modules/05_17_功能模块.md
       E 节奏 → modules/05_12_功能模块.md

  报告分七节，逐条检查，不重叠：

  【第一节 · 五道门禁 A】（逐条）
  1. 引用门禁：对话/叙述中引用的设定、事件、人物是否与已有文档一致
  2. 一致性门禁：人物言行是否与设定性格/当前状态一致（OOC检测）
  3. 蓝图门禁：本章是否偏离大纲规划（出场角色/场景/冲突目标）
  4. 未知实体门禁：是否出现未在设定文档中定义的新地名/组织/能力/物品（未注册实体）
  5. 描写门禁：环境/动作/外貌描写是否自洽、是否有明显感官矛盾

  【第二节 · 强约束 B】（始终PASS，仅提示）
  - 金手指叙事 / 时间约束 / 叙事线监控
  - 零风险 → 静默（报告中仅一句"强约束：PASS，无风险"）
  - 有风险 → 附加风险提示与建议（不阻断流水线）

  【第三节 · 逻辑因果 G】（7 项）
  【写手视角】
  1. 设定不自打架：本章呈现的设定是否与 bible/世界观文档自我一致？（示例："灯长明"与"爷爷禁点"须区分，不可让读者误读为矛盾）
     ★ 设定分层判定规则（防误判）：
     - 前置预埋类（器物常态异象）：道具/异能的常态特征（特殊质感/温度/氛围），必须在高潮前分散预埋暗示；完全无铺垫 = FAIL；仅隐晦铺垫 = PASS（含优化建议）
     - 触发解锁类（激活后次生效果）：道具激活后才出现的衍生能力/代价（灯焰显形/疤痕异动/反噬），允许在高潮首次释放，不要求前置预埋，不算"设定空降"
  2. 信息越级：主角是否说了/想了本章尚未该知道的信息？（示例：第1章不知"灯油=阳寿"却写"抽的是他的寿"→越级）
  3. 角色认知自洽：角色基于已有信息得出的推论/判断，是否与角色自身已知事实矛盾？（示例：亲眼看到人搬进去，却心想"付了租金不住"→认知矛盾）
     ★ 本能行为判定参考（不做强制校验，仅作审稿提醒）：
     - 区分「主动理智抉择」与「绝境本能应激动作」
     - 本能动作若存在童年记忆/感官特质/身体反应等前置线索，不可直接判定为动机断层
     - 仅「无任何前置痕迹的突然反常行为」才可判定为 FAIL；有铺垫但渲染不足 → PASS（含优化建议）

   ★ 配角立体度判定：
   - 按角色类型区分，不按章节号区分：
     · 一次性工具配角（单章出场、仅承担信息传递/背景交代）：允许轻量化，不强制个性细节 → PASS / PASS（含优化建议）
     · 长线出场配角（跨≥3章或设定为常驻/半常驻）：如无专属特征/记忆点 → FAIL
     · 回忆人物（祖辈/已故等）：首现留白制造悬念属合理写法，不扣分；长线未补全 → PASS（含优化建议）

  【读者盲读视角】
  4. 空间矛盾：物体/人物/声音位置是否明确且不矛盾（如灯在主角屋，却写"听见哭声从灯方向来"）
  5. 时间矛盾：跨度/顺序是否合理，有无同时出现在两处
  6. 因果断层：关键情节因→果是否成立，有无机械降神/凭空能力或信息
  7. 视角纯净：有无作者跳视角旁白（主角无此认知的系统/档案/上帝句）

  【第四节 · 读者审稿 C】4 维度评分（连贯/吸引/爽点/bug），按 05_25 格式输出
  【第五节 · 章节质量 F】情节/人物/爽点/设定质量检查，按 05_13 格式输出
  【第六节 · 连贯性 D】人物/剧情/伏笔/世界观跨章连贯，按 05_17 格式输出（读前10章摘要）
  【第七节 · 节奏 E】本章及近程节奏诊断+优化建议，按 05_12 格式输出

  互斥边界：
  -「信息越级」专指主角已知信息的前后一致性
  -「角色认知自洽」专指角色基于已有认知的推理是否自相矛盾
  -「因果断层」专指剧情事件因→果链断裂
  - 同一段落触犯多项时，按最严格标准每项独立判定 FAIL

  每节每条输出格式：
  ✅ 或 ❌ + 具体段落引用 + 矛盾点说明 + 修改建议（含预期正确写法）

  报告写入：{书名}/设定/第NNN章_全量审核报告.md
  最后一行返回总结（三选一）：
  - PASS（七节全✅，无任何问题）
  - PASS（含优化建议）：[N]条建议（有可优化点但非逻辑硬伤，不触发修复）
  - FAIL: [N]个问题需修复（存在逻辑硬伤，必须触发修复子代理）
```

> **摘要数量差异设计说明**：U 一次性读取前 10 章摘要，覆盖 C（读者体验，中等上下文）、D/E（跨章连贯与节奏，长程上下文）的不同需求——D/E 需要更长近期上下文，C 侧重本章自身体验，二者在 U 内部按节分别处理，摘要数量差异是有意为之。

## 三、步骤4 结论收集与修复（★v9.3 重构）

### 4.1 结论收集与分类

等待步骤3 全量子代理 U 返回（单一结论，含七节）。

- ⚠️ **第二节 B（强约束）始终 PASS**：不触发修复，不阻断流水线。
- 按三态分类：

| 状态 | 含义 | 操作 |
|------|------|------|
| `PASS` | 无任何问题 | 标全部对应 .done |
| `PASS（含优化建议）：[N]条` | 有可优化点但非逻辑硬伤（如词汇重复、氛围渲染不足、配角单薄等） | 标全部对应 .done + 主代理记录建议入报告摘要，**不触发修复子代理** |
| `FAIL: [N]个问题` | 存在逻辑硬伤（因果断裂/设定矛盾/OOC等） | **触发修复子代理** |

### 4.2 全 PASS / PASS（建议）路径

U 为 `PASS` 或 `PASS（含优化建议）`、无任何 `FAIL` → 标 `.done_chapter`：

- 逐标记 `.done_gates` / `.done_constraints` / `.done_logic_causal` / `.done_review` / `.done_quality` / `.done_coherence` / `.done_rhythm`
- 如有 `PASS（含优化建议）`项 → 主代理收集所有建议，在流水线总结中汇总输出，但不阻断闭环
- 全部齐备后执行步骤 4.4（报告合并），合并完成后标 `.done_chapter`

### 4.3 修复路径（任一 FAIL 触发）

U 返回 `FAIL` → 启动**独立修复子代理**（只处理 FAIL 项，忽略 PASS（建议）项）：

**修复子代理调用规格**：

```
goal: 根据审核报告修复第NNN章正文中的问题

context: 中文回复。项目目录：{工作目录}，章节文件：{书名}/正文/第NNN章_章节名.txt。
  
  ★ v9.3 关键：你只需读取以下文件，不需要读取记忆文档（bible/arcs/timeline 等）。
  审核报告已经包含了具体段落引用、矛盾点说明和修改建议。

  【必读文件】
  1. {书名}/正文/第NNN章_章节名.txt — 待修复的章节正文
  2. {书名}/设定/第NNN章_全量审核报告.md — 状态为 FAIL 的审核报告

  【修复要求】
  1. 逐条处理审核报告中标记为 ❌ 的问题
  2. 按审核报告中的「修改建议」执行修复
  3. 只修改有问题的段落，保持其余内容不变
  4. 修完后覆盖写入原文件：{书名}/正文/第NNN章_章节名.txt
  5. 在报告末尾追加修复记录：
    
     ---
     ## 修复记录
     - [YYYY-MM-DD] 修复了以下问题：
       1. [问题简述] @[段落位置]
       2. ...
  
  最后一行返回：FIXED: [N]个问题已修复 或 无法修复: [原因]
```

**⚠️ 修复子代理只需要 `toolsets:["file"]`**，不需要读取记忆文档。审核报告已包含：
- 具体段落引用（定位问题位置）
- 矛盾点说明（什么问题）
- 修改建议（预期正确写法，含参考来源）

**修复后二次审核**：
1. 修复子代理完成后 → **重启全量审核子代理 U** 对修复后的章节重新审核（U 为单子代理，重启即全量重审，无需挑选）
2. 二次仍 FAIL → 再次修复（最多 2 轮修复）
3. 2 轮修复后仍 FAIL → 阻断流水线，报告用户等待指示
4. 全部 PASS → 进入步骤5（周期检查）

### 4.4 报告合并（★v9.3 适配）

流水线收尾时（全 PASS 闭环 或 2轮修复后仍阻断），主代理执行报告合并：
1. 读取散报告 `{书名}/设定/第NNN章_全量审核报告.md`
2. 若需统一命名，重命名为：`{书名}/设定/第NNN章_审核报告.md`（U 已是一份完整报告，内容无需拼接）
3. 写入 `.done_merge` 标记

合并后的报告路径为流水线最终产出。修复子代理和二次审核仍使用全量审核报告路径；合并为流水线最后一步，不区分 PASS/阻断。

### .done 标记存储规范

**路径规则**：`[书名]/.done/` 目录下，每个标记为一个空文件。首次使用时需创建 `.done/` 目录。

**完整标记文件名清单**（以第 NNN 章为例）：

```
[书名]/.done/第NNN章_wordcount.done        ← 步骤1 字数通过
[书名]/.done/第NNN章_bible.done            ← 步骤2 圣经更新完成
[书名]/.done/第NNN章_summary.done          ← 步骤2 摘要写入完成
[书名]/.done/第NNN章_gates.done            ← U（五道门禁 A）PASS
[书名]/.done/第NNN章_constraints.done      ← U（强约束 B）PASS（始终PASS）
[书名]/.done/第NNN章_logic_causal.done     ← U（逻辑因果 G）PASS
[书名]/.done/第NNN章_review.done           ← U（读者审稿 C）PASS
[书名]/.done/第NNN章_quality.done          ← U（质量 F）PASS
[书名]/.done/第NNN章_coherence.done        ← U（连贯性 D）PASS
[书名]/.done/第NNN章_rhythm.done           ← U（节奏 E）PASS
[书名]/.done/第NNN章_merge.done            ← 步骤4.4 报告合并完成
[书名]/.done/第NNN章_innovation.done       ← 步骤5 H（创新深度检查）PASS（仅第10/20/30...章）
[书名]/.done/第NNN章_chapter.done          ← 全部完成，章节闭环
```

> **v9.3 标记说明**：标记名与 v9.1/v9.2 完全一致（gates/constraints/logic_causal/review/quality/coherence/rhythm），仅写入主体由 7→3→1，现在全部由单子代理 U 一次性写入。旧项目 `.done` 目录兼容不受影响。

**规则**：
- 每个子代理/步骤完成后，主代理立即写入对应 `.done` 空文件（文件大小=0）
- **`.done_chapter` 闭环条件**：第 N 章的所有**必需**子标记齐备后才写入。必需标记按章节号判断：
  - 所有章：wordcount / bible / summary / gates / constraints / logic_causal / review / quality / coherence / rhythm / merge
  - 第10/20/30...章额外增加：innovation
  - 非10倍数章跳过 innovation.done 检查，不阻塞闭环
- `.done` 文件是流水线状态的唯一真相源；重启/恢复时通过检查 `.done` 目录判断某章完成了哪些步骤

## 四、步骤5 周期性检查（按需触发）

- 每5章：连贯性深度 + 质量深度（复用 D/F 深度模式，报告写入对应章节流水线路径）。深度检查中发现 🔴 需修复项 → 阻断 `.done_chapter` 闭环，触发修复子代理；🟡 建议项不阻断
- 每10章：创新深度（子代理 H）+ 主代理阶段压缩

**H 子代理调用规格（创新深度检查·v9.3 返回完整报告）**：
> 完整调用规格见 `modules/05_14_功能模块.md`。以下为流水线适配摘要：
```
goal: 对小说作品执行创新深度检查，评估情节/人物/主题/设定四维度的创新性与原创度

context: 中文回复。项目目录：{工作目录}。
  ⚠️ mode: pipeline — 由05_26写后流水线步骤5调用。返回完整报告正文（不再仅返回PASS/FAIL一行）。
  需读取：{书名}/设定/{书名}_世界观设定.md、{书名}/设定/{书名}_人设卡.md、{书名}/设定/{书名}_情节大纲.md、
          {书名}/正文/第{NNN-9}章_*.txt ～ {书名}/正文/第NNN章_章节名.txt（最近10章正文）、
          {书名}/设定/创新深度检查报告.md（如已存在则覆盖）。
  检查维度：
  1. 情节创新：是否避免常见套路，是否有新颖性和意外性
  2. 人物创新：是否立体多面，成长是否自然，关系是否复杂
  3. 主题创新：是否有深度，价值观是否独特，是否有社会意义
  4. 设定创新：世界观是否独特，规则是否自洽，是否有创意

  报告写入：{书名}/设定/创新深度检查报告.md
  最后一行返回总结（三选一）：PASS / PASS（含优化建议） / FAIL: [N]个问题需修复
```

- 每50章：主代理卷压缩 + 复查高重要度伏笔近况
