# 功能模块 26：写后流水线（强制·每章必跑）
>
> **功能编号**：26
> **功能定位**：单章正文通过字数检查后，执行"主代理记忆维护 + 子代理审核 + 子代理修复"的完整闭环。
> **铁律**：第 N 章全部 PASS + .done 标齐，**才允许写第 N+1 章**。黄金开篇"第1-3章"也必须逐章闭环，禁止连写再补审。
> - *非章节·分段模式（短篇）：逐段轻量写+存（**每段跑字数脚本 + 步骤2 的记忆维护增量**，不做步骤1 的 .done 判定，故逐段无 .done 标记），**不逐段硬卡审核门禁**；全部段写完后，对整篇（全部段拼接）一次性跑完整审核（步骤3 的 U 八项 G/D + 步骤4 朱雀六指标按整篇），整篇全 PASS + 整篇 .done 标齐才算完稿。逐段期间的记忆维护累计为整篇连贯性基准。*

---

## 零、前置检查（步骤0；记忆系统就绪验证）

> 写后流水线依赖记忆系统（圣经/摘要/阶段）的正常运转。如果记忆系统未初始化，流水线的步骤2（圣经更新）和所有子代理将无法读取所需文件。

**执行逻辑**：
1. 检查 `[书名]/记忆系统/圣经/` 目录下的 5 个圣经文档是否全部存在：
   - 故事圣经.md / 人物弧线.md / 剧情时间线.md / 伏笔清单.md / 角色数据库.md
2. **全部存在** → 记忆系统已初始化，正常进入步骤1
3. **任一缺失** → **直接终止**：新架构（存在 `_state.json`）→ `state_render.py --project` 重渲染 + `state_commit check` 复核；无 state → 提示用户执行功能18初始化记忆系统。记忆系统是写后流水线的硬性前提。

## 一、总流程（顺序不可跳）

```
1. 字数确认（复用 03_06 步骤4 脚本结果）→ 立即写入 `.done_wordcount`；正文定稿随手 `text_guard digest` 记指纹（五·文本指纹，每章必跑；**流水线内任何落盘改稿——4.1e 人工段注入/整段重生/强化轮、4.3 修复轮——交付后立即重跑**，以最终稿为准，完整触发面见五·文本指纹）
2. 主代理更新 5 圣经 + 摘要 → 完成后写入 `.done_bible` + `.done_summary`
步骤3  单子代理 U（全量审核，合并 A/B/G/C/F/D/E/H 八项，一次调用）：
         读取全套文件 → 输出一份完整审核报告 → 末行三态总结
步骤4  收集结论 → 无论 PASS/FAIL 均先做 4.1b–4.1e（分布/用词/六指标/人工证据包）→ 写 `.done_zhuque`；有 FAIL/建议 → 独立修复子代理后再复核；全 PASS 且 zhuque 齐 → 步骤4.4 merge → **新架构项目（存在 `_state.json`）：`state_commit commit` 写 `.done_state`（五·状态提交）** → 才可标 chapter
步骤5  周期检查（每5/10/50章触发）
步骤6  写章节档案文件（报告/第NNN章_章节档案.md；正文全程不留元数据）
步骤7  输出【第NNN章状态】回执（格式见 modules/00_强制执行协议.md；无回执=违规）
```
> - *非章节·分段模式（短篇，整篇单文件）：不逐段跑以上流程。逐段仅做**字数脚本 + 步骤2 的轻量记忆维护**（圣经/摘要增量更新，整篇一份摘要不拆段），**不逐段落 .done 标记**；全部段写完后，对**整篇单文件**一次性跑步骤1（整篇字数判定，带容差不硬卡，此时才写 `.done_wordcount`）→ 步骤2（整篇摘要定稿）→ 步骤3（U 八项按整篇）→ 步骤4（朱雀 4.1b–4.1e 含人工证据包，按整篇），整篇全 PASS + 整篇 `.done` 标齐才算完稿。一步到位：逐段无 .done，`.done` 只在整篇收尾时一次标齐；无每50段周期检查（短篇段数不足以到达该节点）*

> **执行铁律**：U 返回完整报告（非仅 PASS/FAIL 一行），修复子代理直接读报告定位问题，无需重读记忆文档；B（强约束）始终 PASS 不阻断；审核(U)与修复由不同子代理完成，避免自审偏见（**例外**：delegate_task 不可用时主代理降级自审，见步骤3 前置检查）。
> **闭环铁律**：`.done_zhuque`（4.1b–4.1e 人工证据包）为章节闭环必需；缺任一必需 `.done` → 禁止 `.done_chapter`、禁止写 N+1；结束必须输出【第NNN章状态】回执。

### 步骤2 详细：主代理更新 5 圣经 + 摘要（★权威定义，03_06 步骤5→03_26 步骤2 唯一权威定义）

> 本步骤是主代理唯一保留的动手环节（编辑职责）。主代理阅读写作子代理产出的正文，更新记忆系统。
>
> **新架构分流（存在 `记忆系统/_state.json`）**：本节第 1–5 条产出改为填入「五·状态提交」事务 JSON 的 delta（含摘要/伏笔状态/时间线条目/角色快照），由 `state_commit commit` 渲染派生件——**禁手改派生文件**（直接改会被 state_commit check 点名 FAIL 并被重渲染覆盖）；旧项目（无 `_state.json`）按第 1–6 条手写。角色数据库两架构均手写登记（非派生件，见 03_18 总则）。

1. 生成单章摘要（L2）
   - 按照 `[书名]/记忆系统/摘要/模板.md` 的格式
   - 写入 `[书名]/记忆系统/摘要/第{NNN}章摘要.md`
   - 包含：核心事件 / 人物变化（情绪/关系/目标）/ 新埋设伏笔（同步 伏笔清单.md）/ 已回收伏笔（同步 伏笔清单.md）/ 本章结尾悬念 / 下一章方向建议
   - *非章节·分段模式（短篇整篇单文件）：不写"第NNN段摘要"，整篇写一份 `[书名]/记忆系统/摘要/{书名}_整篇摘要.md`；逐段期间的记忆维护增量并入这份整篇摘要，全部段写完后定稿*
2. 更新故事圣经（故事圣经.md）：当前状态快照（结尾场景/人物在场/最后一句话/主角目标/主要障碍/读者悬念）、当前已写章节计数
3. 更新人物弧线（人物弧线.md）：本章涉及角色的演化记录（情绪/关系/目标变化）+ 当前状态段落
   - 同步更新角色数据库（角色数据库.md）：出场/退场事件、能力状态变化、物品持有变动、关系快照
4. 更新剧情时间线（剧情时间线.md）：
   - 在主线时间线表格中追加本章事件，**必须加标签**（[主线]/[支线X]/[交叉]）
   - 更新活跃支线状态表（上次活跃章节/当前状态/核心悬念）
   - 更新支线详情中的事件时间线
   - 关键物品/线索有变动时更新追踪表
5. 更新伏笔清单（伏笔清单.md）：新埋设→添加（状态🔘已埋设，记首现章）；已回收→标记✅并追近况；🔄准备回收→检查本章是否回收/是否过期（>预期+10章标⚠️）
6. 旧项目（无 `_state.json`）追加事实台账：本章可变事实（境界/伤势/天数/物品增减）写入 `记忆系统/圣经/事实台账.md`（口径 `templates/事实台账模板.md`；新架构由 `state_commit` 渲染，禁手改）

## 二、步骤3 全量子代理 U 审核规格

> **前置检查**：启动子代理前，验证 `delegate_task` 工具可用。
> - 主代理**必须先实际调用一次 `delegate_task`**（最小任务探测：如「返回 OK」）确认是否真不可用；不得仅凭"未配置/以为不可用"主观判断降级。
> - 探测成功 → 正常走子代理 U。
> - 探测确失败（调用报错/超时/无返回）→ **主代理降级自审**：按步骤3 的 U 八节规格通读正文+记忆系统出同格式报告，**向用户说明降级原因**；报告注明 `Fallback: delegate_task unavailable -> main-agent self-review`（自审=只出报告，修复仍按报告执行，不视为铁律违反）。
>
> **⚠️ 子代理启动前必须加载源模块**：详细检查维度与报告格式定义在对应源模块中。主代理在 invoke delegate_task 前，应读取以下源模块并将关键格式要求注入子代理 context：
> - B（强约束）→ `read_file("modules/03_22_功能模块.md")` 子代理调用规格节
> - C（读者审稿）→ `read_file("modules/03_25_功能模块.md")` delegate_task 调用模板
> - F（质量）→ `read_file("modules/03_13_功能模块.md")` 子代理调用规范
> - D（连贯性）→ `read_file("modules/03_17_功能模块.md")` 子代理调用规格
> - E（节奏）→ `read_file("modules/03_12_功能模块.md")` 子代理调用规格
> - H（叙事规则）→ `read_file("modules/03_24_功能模块.md")` 二阶五维审查节 + 规则集文件（`{书名}/设定/{书名}_规则集.md` 或 `references/rulesets/通用默认.md`）
> - A 五道门禁、G 逻辑因果为内联定义（下方已包含完整调用模板）。
>
> 通过 `delegate_task` **单次启动**全量审核子代理 U（`toolsets:["file"]`，U 可自行读取上述源模块获取详细格式）。
> context 必含：项目工作目录、章节文件名、所需读取文件清单、`mode: pipeline` 标识。
>
> **★ 关键：子代理返回完整报告，而非仅 PASS/FAIL。** 完整报告用于步骤4 修复子代理直接定位问题，无需修复子代理重读记忆文档。

**U 全量审核子代理调用规格（合并 A/B/G/C/F/D/E/H 八项）**：

```
goal: 对第NNN章执行全量审核（合并原8子代理：五道门禁A + 强约束B + 逻辑因果G + 读者审稿C + 质量F + 连贯性D + 节奏E + 叙事规则H），输出一份完整审核报告

context: 中文回复。项目目录：{工作目录}，章节文件：{书名}/正文/第NNN章_章节名.txt。
  ⚠️ mode: pipeline — 由03_26写后流水线步骤3调用。返回完整报告正文（不再仅返回PASS/FAIL一行）。
  需读取文件清单（U 可自行用 file 工具读取）：
   - 章节正文：{书名}/正文/第NNN章_章节名.txt
   - 设定：{书名}/设定/{书名}_世界观设定.md、{书名}/设定/{书名}_人设卡.md、{书名}/设定/{书名}_情节大纲.md
   - 圣经：{书名}/记忆系统/圣经/故事圣经.md、人物弧线.md、剧情时间线.md、伏笔清单.md、角色数据库.md
   - 摘要：{书名}/记忆系统/摘要/第{NNN-10}章摘要.md ～ 第{NNN-1}章摘要.md（前10章摘要，供连贯性/节奏/读者体验使用；不足 10 章时有多少读多少）
   - 规则集（H 叙事规则用）：优先 `{书名}/设定/{书名}_规则集.md`（内容记录规则集路径），无此文件 → 直接读 `references/rulesets/通用默认.md`
   - 详细格式与维度定义（U 应读取以遵循规范）：
       B 强约束 → modules/03_22_功能模块.md
       C 读者审稿 → modules/03_25_功能模块.md
       F 质量 → modules/03_13_功能模块.md
       D 连贯性 → modules/03_17_功能模块.md
       E 节奏 → modules/03_12_功能模块.md
       H 叙事规则 → modules/03_24_功能模块.md（二阶五维审查）+ 规则集文件（见下）

  报告分八节，逐条检查，不重叠：

  【第一节 · 五道门禁 A】（逐条）
  1. 引用门禁：对话/叙述中引用的设定、事件、人物是否与已有文档一致
  2. 一致性门禁：人物言行是否与设定性格/当前状态一致（OOC检测）
  3. 蓝图门禁：本章是否偏离大纲规划（出场角色/场景/冲突目标）
  4. 未知实体门禁：是否出现未在设定文档中定义的新地名/组织/能力/物品（未注册实体）
  5. 描写门禁：环境/动作/外貌描写是否自洽、是否有明显感官矛盾

  【第二节 · 强约束 B】（始终PASS，仅提示）
  - 金手指叙事 / 时间约束 / 叙事线监控
  - 零风险 → 静默（报告中仅一句"强约束：PASS，无风险"）
  - 有风险 → 附加风险提示与建议（不阻断流水线）

  【第三节 · 逻辑因果 G】（7 项）
  【写手视角】
  1. 设定不自打架：本章呈现的设定是否与 圣经/世界观文档自我一致？（示例："灯长明"与"爷爷禁点"须区分，不可让读者误读为矛盾）
     ★ 设定分层判定规则（防误判）：
     - 前置预埋类（器物常态异象）：道具/异能的常态特征（特殊质感/温度/氛围），必须在高潮前分散预埋暗示；完全无铺垫 = FAIL；仅隐晦铺垫 = PASS（含优化建议）
     - 触发解锁类（激活后次生效果）：道具激活后才出现的衍生能力/代价（灯焰显形/疤痕异动/反噬），允许在高潮首次释放，不要求前置预埋，不算"设定空降"
  2. 信息越级：主角是否说了/想了本章尚未该知道的信息？（示例：第1章不知"灯油=阳寿"却写"抽的是他的寿"→越级）
  3. 角色认知自洽：角色基于已有信息得出的推论/判断，是否与角色自身已知事实矛盾？（示例：亲眼看到人搬进去，却心想"付了租金不住"→认知矛盾）
     ★ 本能行为判定参考（不做强制校验，仅作审稿提醒）：
     - 区分「主动理智抉择」与「绝境本能应激动作」
     - 本能动作若存在童年记忆/感官特质/身体反应等前置线索，不可直接判定为动机断层
     - 仅「无任何前置痕迹的突然反常行为」才可判定为 FAIL；有铺垫但渲染不足 → PASS（含优化建议）

   ★ 配角立体度判定：
   - 按角色类型区分，不按章节号区分：
     · 一次性工具配角（单章出场、仅承担信息传递/背景交代）：允许轻量化，不强制个性细节 → PASS / PASS（含优化建议）
     · 长线出场配角（跨≥3章或设定为常驻/半常驻）：如无专属特征/记忆点 → FAIL
     · 回忆人物（祖辈/已故等）：首现留白制造悬念属合理写法，不扣分；长线未补全 → PASS（含优化建议）

  【读者盲读视角】
  4. 空间矛盾：物体/人物/声音位置是否明确且不矛盾（如灯在主角屋，却写"听见哭声从灯方向来"）
  5. 时间矛盾：跨度/顺序是否合理，有无同时出现在两处
  6. 因果断层：关键情节因→果是否成立，有无机械降神/凭空能力或信息
  7. 视角纯净：有无作者跳视角旁白（主角无此认知的系统/档案/上帝句）

  【第四节 · 读者审稿 C】4 维度评分（连贯/吸引/爽点/bug），按 03_25 格式输出
  【第五节 · 章节质量 F】情节/人物/爽点/设定质量检查，按 03_13 格式输出
  【第六节 · 连贯性 D】人物/剧情/伏笔/世界观跨章连贯，按 03_17 格式输出（读前10章摘要）
  【第七节 · 节奏 E】本章及近程节奏诊断+优化建议，按 03_12 格式输出

  【第八节 · 叙事规则审查 H】
  - 规则集选择：优先读 `{书名}/设定/{书名}_规则集.md`（用户通过功能24 `规则集`/`加载规则集` 选定后生成）；不存在 → 用 `references/rulesets/通用默认.md`
  - 按所选规则集的五维定义逐条审查本章（每维 ✅/❌ + 段落引用 + 修改建议）：
    1. 能力因果法则：力量/能力的使用是否遵循完整逻辑链（动机→判断→行动→结果），有无空降解围/无铺垫能力空降
    2. 代价显性法则：每次使用能力是否支付了可感知代价，代价描写是否与能力级别匹配（按规则集代价表）
    3. 空间连续法则：跨区域移动是否有合理耗时（按规则集耗时基准，短/中/长/跨世界分档）
    4. 因果不可逆法则：死亡/关键损毁/身份暴露/关系变化等是否被不合理翻转（死亡绝对不可逆；恢复需世界规则允许+对等代价）
    5. 资源约束追踪：资源消耗是否与剧情匹配，有无资源无端恢复/超规格使用（按规则集资源池字段）
  - 与第三节 G 的互斥边界：G 管"本章内部逻辑自洽"（信息越级/认知矛盾/因果断层），H 管"叙事规则维度的量化约束"（能力代价/空间耗时/资源账本）——同一段落触犯多项时按最严格标准独立判定

  互斥边界：
  -「信息越级」专指主角已知信息的前后一致性
  -「角色认知自洽」专指角色基于已有认知的推理是否自相矛盾
  -「因果断层」专指剧情事件因→果链断裂
  - 同一段落触犯多项时，按最严格标准每项独立判定 FAIL

  每节每条输出格式：
  ✅ 或 ❌ + 具体段落引用 + 矛盾点说明 + 修改建议（含预期正确写法）

  报告写入：{书名}/报告/第NNN章_全量审核报告.md
  最后一行返回总结（三选一）：
  - PASS（八节全✅，无任何问题）
  - PASS（含优化建议）：[N]条建议（有可优化点但非逻辑硬伤，不触发修复）
  - FAIL: [N]个问题需修复（存在逻辑硬伤，必须触发修复子代理）
```

### 4.1c 用词检查（AI味词密度）

4. 2 轮修复后仍有 FAIL → 阻断流水线，报告用户等待指示
5. 全部 PASS（无建议）→ **确认 4.1b–4.1e 已执行且 `.done_zhuque` 已写入**（未执行则先补跑，PASS 不豁免）→ **本轮修复若改动过正文：重跑 `text_guard digest` 刷新指纹为最终稿**（授权更新；否则五·文本指纹 verify 会按旧稿报不一致、误触停下询问）→ **若修复改动超过约 15% 正文或删除/重写了报告「人工证据包」以外的大段内容，必须补跑 4.1e 人工证据密度自查并更新报告后再闭环**（**轮交付后、闭环前度量**；阈值由主代理按 diff 自判）→ 再进入步骤5（周期检查）

**保留原稿与停止线（P2-12）**：
1. **修复前备份**：任一修复轮开始前，先把 `正文/第NNN章_*.txt` 复制为 `.story/work/第NNN章/原稿.txt`（原稿永不覆盖、永不删除）
2. **阻断即保留并存**：2 轮修复后仍 FAIL → 除第4条的阻断报告外，**原稿与最新修复稿并存**（各自路径写进报告），不标 zhuque/chapter、不写 N+1
3. **超范围停止线**：修复改动 >15% 正文或删除/重写了报告「人工证据包」以外的大段内容 → 立即停止本轮修复，回退原稿后重派（**轮中检测、修复未交付时执行**；与 4.3 步骤5 同源分工：4.3 步骤5=轮后度量补跑自查、本条=轮中即停回退，同一阈值按交付节点分用）
4. **事实复验失败**：修复后圣经/事实台账与正文冲突且无法在改最少原则内消解 → 停止修复，按第2条处置，**禁止带伤闭环**

### 4.4 报告合并

流水线收尾时（全 PASS 闭环 或 2轮修复后仍阻断），主代理执行报告合并：
1. U 报告即本章流水线的最终报告产物：`{书名}/报告/第NNN章_全量审核报告.md`（内容无需拼接，不再重命名）
2. 写入 `.done_merge` 标记

修复与二次审核共用同一报告路径；合并为步骤4 最后一步（其后步骤5 周期检查、步骤6 档案），不分 PASS/阻断。

### .done 标记存储规范

**路径规则**：`[书名]/.done/` 目录下，每个标记为一个空文件。首次使用时需创建 `.done/` 目录。

**完整标记文件名清单**（以第 NNN 章为例）：

```
[书名]/.done/第NNN章_wordcount.done        ← 步骤1 字数通过
[书名]/.done/第NNN章_bible.done            ← 步骤2 圣经更新完成
[书名]/.done/第NNN章_summary.done          ← 步骤2 摘要写入完成
[书名]/.done/第NNN章_zhuque.done           ← 步骤4.1b–4.1e 朱雀预检与人工证据包完成（闭环必需）
[书名]/.done/第NNN章_gates.done            ← U（五道门禁 A）PASS
[书名]/.done/第NNN章_constraints.done      ← U（强约束 B）PASS（始终PASS）
[书名]/.done/第NNN章_logic_causal.done     ← U（逻辑因果 G）PASS
[书名]/.done/第NNN章_review.done           ← U（读者审稿 C）PASS
[书名]/.done/第NNN章_quality.done          ← U（质量 F）PASS
[书名]/.done/第NNN章_coherence.done        ← U（连贯性 D）PASS
[书名]/.done/第NNN章_rhythm.done           ← U（节奏 E）PASS
[书名]/.done/第NNN章_merge.done            ← 步骤4.4 报告合并完成
[书名]/.done/第NNN章_state.done            ← 新架构项目由 `state_commit commit` 自动写（存在 `_state.json` 时必需，共 13 项，见第七节）
[书名]/.done/第NNN章_constraint_warning.done ← 步骤5 约束量化检查 ⚠️（趋势未修正；恢复时删除。**非闭环必需标记**，不阻塞 .done_chapter；供下一章写作读趋势提示）
[书名]/.done/第NNN章_innovation.done       ← 步骤5 创新深度检查 PASS（仅第10/20/30...章）
[书名]/.done/第NNN章_chapter.done          ← 全部完成，章节闭环
```

> **`.done` 标记**：**七项** U 标记名固定（gates/constraints/logic_causal/review/quality/coherence/rhythm，均由单子代理 U 一次性写入）；另有流水线标记 **zhuque**（4.1b–4.1e 人工证据包）为闭环必需；U 的第八项 H（叙事规则审查）**不单独落标记**，结论并入全量审核报告；旧项目 `.done` 目录兼容不受影响。
> **步骤6 无 `.done` 标记**：章节档案文件的产出状态不单独落标记（闭环判定以第七节 `.done` 清单为准），因此 `.done` 清单不含步骤6；闭环判定不受其影响。

**规则**：
- 每个子代理/步骤完成后，主代理立即写入对应 `.done` 空文件（文件大小=0）
- **`.done_chapter` 闭环条件**：第 N 章的所有**必需**子标记齐备后才写入。必需标记按章节号判断：
  - 所有章：wordcount / bible / summary / **zhuque** / gates / constraints / logic_causal / review / quality / coherence / rhythm / merge（新架构项目另含 **state**，共 13 项，见第七节）
  - 第10/20/30...章额外增加：innovation
  - 非10倍数章跳过 innovation.done 检查，不阻塞闭环
- `.done` 文件是流水线状态的唯一真相源；重启/恢复时通过检查 `.done` 目录判断某章完成了哪些步骤
- `报告/第NNN章_章节档案.md`（步骤6 产出）是**审计留痕 + 参数链存档**，**不作状态判定**：完成状态一律以 `.done/` 空标记为准（该文件已废除「完成步骤」字段，不复制状态）。档案的归一化由「补缺」负责（见 `modules/03_26B_补缺执行规格.md`）

## 五·状态提交（新架构项目·存在 `记忆系统/_state.json` 时必跑；总流程步骤4 尾、chapter 前）

**触发**：`.done_merge` 之后、`.done_chapter` 之前；旧项目（无 `_state.json`）跳过本步。

1. **构造事务 JSON**：只填 delta（变化角色快照 / 本章事实 / 时间线条目 / 摘要 / 字数 / 伏笔状态 / 变化时的 `overview`（状态快照 summary·snapshot、阶段 stages）与 `context`（position、近三章 recent_chapters、下一章承诺 next_chapter_commitments）），写入 `{书名}/.story/work/第NNN章/state.json`；可用 `draft` 预填骨架。
2. **提交**：`python scripts/state_commit.py commit --project "[书名]" --chapter N --input {书名}/.story/work/第NNN章/state.json`（无 Python 环境用 `pwsh scripts/state_commit.ps1 -Command commit -Project "[书名]" -Chapter N -InputFile …`）
   → 成功自动完成：`_state.json` revision+1 → 重渲染全部派生 → **自动创建 `.done/第NNN章_state.done`** → 删除事务文件。
3. **校验**：`state_commit check --project "[书名]"`（从 state 重渲染并逐字节比对；手改派生会被点名）。
4. **失败处置**：校验失败 → 改事务重跑；写入失败 → 修正环境后**重跑同一份 commit**（事务保留）；若 `_state.json` 已推进而派生写失败（脚本 rc1 中止）→ 勿重跑 commit（会被 stale 拒），改跑 `state_render.py --project` 补渲染后 `state_commit check` 复核；`stale transaction` → 重跑 `draft` 取新 `expected_state_revision`。
5. **双实现**：py 为权威、ps1 为兜底；两者渲染逐字节一致（py 提交的项目 ps1 可校验，反之亦然，见回归）。

## 五·文本指纹与手改保护（每章必跑；总流程步骤1 尾首记，修复轮改稿后重跑；以最终稿为准）

**触发**：正文定稿、`.done_wordcount` 之后（步骤1 尾首记）；**流水线内任何落盘改稿交付后必须重跑 `digest` 刷新为最终稿——含 4.1e 人工段注入/高疑似段整段重生/证据强化轮（4.2 步骤1、4.3 步骤5 补跑）与 4.3 修复轮改稿（步骤4.3 第5条）**；retcon 改旧章时同样适用。

> **完成判定（客观可核验，非 .done 项）**：`.story/text-digests.json` 含本章记录 = 本步已执行；`verify` exit2 = 未记即本步缺失，补跑 `digest`。本步不落 `.done`（指纹账本即客观证据，第七节清单不含本步），跨会话恢复/整书巡检用第4条 `verify-all` 复核。

1. **记指纹**：`python scripts/text_guard.py digest --project "[书名]" --chapter N`（`pwsh scripts/text_guard.ps1 -Command digest -Project … -Chapter N` 同口径；写 `.story/text-digests.json`，原子替换）
2. **改旧章前先核对**：`text_guard verify --project "[书名]" --chapter N`
   - `一致` → 继续
   - `与记录不一致（exit1）` → **停下询问**：沿用旧稿 / 按新稿重写 / 只看不处理；**不得静默覆盖**
   - `无指纹记录（exit2）` → 该章先 `digest` 补记
3. **retcon 留痕**：按确认结论处理后重跑 `digest` 刷新指纹，并在 `设定/修订留痕.md` 追加一行（章节/时间/原摘要/新内容/原因）
4. **整书巡检**：跨会话恢复或「补缺」前可跑 `text_guard verify-all --project "[书名]"`（exit1 = 有章被手改 → 逐章按第2条处置）
